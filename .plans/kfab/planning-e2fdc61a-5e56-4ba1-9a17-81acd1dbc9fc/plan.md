# Implementation plan

## Change title

fix(web): validate amountCents in user.changeAutoTopUpPaymentMethod against the auto-top-up allow-list

## Problem

Production Sentry issue KILOCODE-WEB-28HA (2 unhandled events, one account, release e009d438) shows POST /api/trpc/user.changeAutoTopUpPaymentMethod failing inside Stripe checkout.sessions.create with "Invalid integer: 0.5" and "Invalid non-negative integer". The procedure declares its input as `z.object({ amountCents: z.number().optional() }).optional()`, with no integer, sign, or allow-list check. It forwards the value as the principal line item's `unit_amount`. Sibling procedures toggleAutoTopUp and updateAutoTopUpAmount already use AutoTopUpAmountCentsSchema (2000 | 5000 | 10000). So malformed client input becomes a 500 plus Sentry noise instead of a 4xx validation error, and any integer amount gets past the documented allow-list.

## Desired outcome

user.changeAutoTopUpPaymentMethod accepts only an omitted amountCents (defaults to 5000) or one of the allowed personal auto-top-up amounts. Anything else fails tRPC input validation with a BAD_REQUEST before charge-risk checks or any Stripe call. The checked-in profile UI keeps working, even for accounts whose stored amount is a legacy value outside the allow-list.

## Scope

- Change the changeAutoTopUpPaymentMethod input schema to `z.object({ amountCents: AutoTopUpAmountCentsSchema.optional() }).optional()`, matching toggleAutoTopUp.
- Narrow createAutoTopUpSetupCheckoutSession's amountCents parameter type to AutoTopUpAmountCents (default DEFAULT_AUTO_TOP_UP_AMOUNT_CENTS), so the type system blocks unvalidated callers.
- Make getAutoTopUpPaymentMethod return a validated amount: safeParse config.amount_cents with AutoTopUpAmountCentsSchema and fall back to DEFAULT_AUTO_TOP_UP_AMOUNT_CENTS instead of the unchecked cast. This stops the UI from echoing an invalid stored value back into the newly strict mutation.
- Add router tests for user.changeAutoTopUpPaymentMethod with the Stripe client mocked, following organization-auto-top-up-router.test.ts.

## Exclusions

- No change to the service-fee preparation tolerance in packages/web-shared/src/lib/service-fees/checkout.ts. With the input validated, an invalid principal can no longer reach it.
- No generic mapping of Stripe errors to tRPC client errors. Real Stripe or transport failures keep their current handling.
- No data migration or backfill of auto_top_up_configs.amount_cents.
- No hand edits to services/kilo-mcp/catalog.json. Its CI workflow regenerates it from the router schema.
- Organization auto-top-up routers already use OrgAutoTopUpAmountCentsSchema and are unchanged.
- The Google Play sibling issues #9059 and #9061 are out of scope.

## Approach

- In apps/web/src/routers/user-router.ts, replace `z.number().optional()` in changeAutoTopUpPaymentMethod with `AutoTopUpAmountCentsSchema.optional()` and keep the `?? DEFAULT_AUTO_TOP_UP_AMOUNT_CENTS` default (equal to 5000). Zod then rejects 0.5, negatives, and non-allow-listed integers with BAD_REQUEST before assertChargeAllowed, reportChargeAttempted, or Stripe run.
- In apps/web/src/lib/stripe/index.ts, type createAutoTopUpSetupCheckoutSession's third parameter as AutoTopUpAmountCents, imported from @kilocode/web-shared/lib/autoTopUpConstants. Both callers in user-router already pass schema-validated values once the input change lands.
- In getAutoTopUpPaymentMethod, replace `(config?.amount_cents as AutoTopUpAmountCents) ?? DEFAULT...` with an AutoTopUpAmountCentsSchema.safeParse fallback, mirroring parseOrgAutoTopUpThresholdCents. Optionally add a small `parseAutoTopUpAmountCents` helper next to it in autoTopUpConstants.ts.
- Add apps/web/src/routers/user-router.auto-top-up.test.ts (or extend an existing user-router test file). Use createCallerForUser and a jest mock of @kilocode/web-shared/lib/stripe-client (as in the org test). Cover: fractional and negative amounts rejected with BAD_REQUEST and checkout.sessions.create not called; a non-allow-listed integer such as 1 rejected; an allowed amount and an omitted amount succeed with the expected unit_amount; getAutoTopUpPaymentMethod returns the default for a stored non-allow-listed integer.

## Affected areas

- apps/web/src/routers/user-router.ts (changeAutoTopUpPaymentMethod input, getAutoTopUpPaymentMethod amount normalization)
- apps/web/src/lib/stripe/index.ts (createAutoTopUpSetupCheckoutSession parameter type)
- packages/web-shared/src/lib/autoTopUpConstants.ts (optional parse helper)
- New or extended user-router auto-top-up test file under apps/web/src/routers/
- services/kilo-mcp/catalog.json (regenerated by CI because the input schema changes; not hand-edited)

## Acceptance criteria

### ac-1: Calling user.changeAutoTopUpPaymentMethod with amountCents 0.5, a negative value, or an integer outside {2000, 5000, 10000} (e.g. 1) fails with tRPC code BAD_REQUEST, and the mocked Stripe checkout.sessions.create is never called. This covers the fail-fast half of the Failure UX guidance: malformed input now gets an immediate, specific validation error instead of a Stripe 500.

**Verification:** Code review

### ac-2: Calling user.changeAutoTopUpPaymentMethod with no input, or with amountCents 2000, 5000, or 10000, still returns a redirectUrl. The Stripe session params carry line_items[0].price_data.unit_amount equal to the requested amount, or 5000 when omitted. Valid requests and genuine Stripe failures behave as before.

**Verification:** Code review

### ac-3: user.getAutoTopUpPaymentMethod returns amountCents equal to DEFAULT_AUTO_TOP_UP_AMOUNT_CENTS when the stored auto_top_up_configs.amount_cents is outside the allow-list, and returns the stored value when it is allowed. The profile UI therefore never sends a value the stricter mutation rejects.

**Verification:** Code review

### ac-4: createAutoTopUpSetupCheckoutSession's amountCents parameter is typed AutoTopUpAmountCents, so passing an unvalidated `number` is a type error.

**Verification:** Source review

## Risks

- Accounts with a legacy stored amount outside the allow-list would have had the UI echo it back and get rejected. The getAutoTopUpPaymentMethod normalization (AC3) prevents that. The trade-off: the UI shows $50 for such accounts until the user picks an amount.
- External callers (kilo-mcp tool wrapper, scripts) that send arbitrary amounts will now get BAD_REQUEST. This is intended, because they were previously failing in Stripe or bypassing the allow-list.
- The kilo-mcp catalog CI workflow will produce a catalog diff for the changed input schema. That is expected noise in the PR.

## Assumptions

- The personal auto-top-up allow-list (2000/5000/10000) is the intended product constraint for the change-payment-method flow as well. The sibling procedures and the schema comment support this.
- The exact client that sent 0.5 is unknown (no request payloads are available), but the server-side fix does not depend on it.
- Router tests run in the existing apps/web jest setup with a database, as organization-auto-top-up-router.test.ts does.

## Decisions

### d-1: Constrain the input with the existing AutoTopUpAmountCentsSchema rather than a looser positive-integer check.

**Answer:** Use AutoTopUpAmountCentsSchema to stay consistent with toggleAutoTopUp/updateAutoTopUpAmount and enforce the documented allow-list.

**Blocking:** no

### d-2: Do not add a separate runtime guard or Stripe-error mapping inside createAutoTopUpSetupCheckoutSession.

**Answer:** Rely on input validation plus a narrowed parameter type; both call sites are schema-validated, so an extra runtime guard would be redundant.

**Blocking:** no
