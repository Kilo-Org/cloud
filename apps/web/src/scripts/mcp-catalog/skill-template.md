# Kilo MCP

General account connections expose the Kilo API through two tools, `kilo_search`
and `kilo_call`. Parent-scoped Cloud Agent connections instead expose the dedicated
child-session tools described below. Use the tool names published by your client;
it may prefix them with the MCP server name.

See `services/kilo-mcp/CHANGELOG.md`.

## General API connections

1. **Search first.** `kilo_search` finds catalog endpoints. Never call a path from memory, and never guess one from this skill.
2. **Call one path.** `kilo_call` takes a `path` from the catalog and an `input` that satisfies that row's `inputSchema`. A path outside the catalog and an input that violates the schema are rejected before any request is made.
3. **Check the kind.** Every row carries a `kind`: `"query"` reads data, `"mutation"` changes it. Call a mutation path only when the user asked for that change.
4. **Retry with care.** On a mutation, an ambiguous transport error — a timeout, a dropped connection, an unknown outcome — leaves the result unknown. Check the current state before a retry. A query carries no such ambiguity and can be retried.

A catalog row carries `path` (the `kilo_call` argument), `kind`, `summary`,
`inputSchema`, `tags`, and `searchBlob` — the text search matches. A row behind
an admin guard carries `admin: true`; an opted-in admin connection also gets
`call_protected`, which fixes a reviewed admin or debug call and its payload,
and `submit_otp`, which runs it once the user approves with their authenticator
code. A row whose top segment is `debug` carries `debug: true`.

The catalog at `services/kilo-mcp/catalog.json` is authoritative.
Read it for current endpoint details.

## Parent-scoped child sessions

Use the published dedicated tools, not API `search` or `call`. A workspace manages
only its direct children. Each child can manage its own children.

- Find repository and branch choices with `list_repositories` and `list_branches`.
  Use `list_environments` to find an environment ID for the launch repository.
- Launch with one repository source, or use `stackOnWorktreeId` alone for your
  own worktree or a direct child's worktree. Include a complete prompt and a fresh
  `operationKey`. Use an exact `search_models` result; do not invent model IDs.
- Prefer callbacks. Use `workspace:<session-id>` with the session ID from
  `cloud-agent-context` to notify this chat. Use `workspace:new-chat` when the
  parent has a worktree. Answer pending child questions with `answer_question`.
- Read history with `get_session_messages` and artifacts with `list_child_artifacts`.
  `create_child_chat` registers another manageable chat without sending work.
- Use `generate_message_id` before a new follow-up. Reuse the original IDs when
  retrying the same request, and check state first if the outcome is unknown.
- `autoCommit` is per message and does not prevent manual Git actions. Put any
  publication restrictions in the prompt.

### Examples

Pseudocode; `modelId` comes from `search_models`; `launchUuid` is a fresh retained UUID.

```js
const child = await spawn_session({
  githubRepo: 'owner/repo', model: modelId, mode: 'code',
  prompt: 'Fix the bug, run focused tests, and report. Do not commit, push, or create a PR.',
  operationKey: launchUuid, autoCommit: false,
  callbackTarget: { url: 'workspace:new-chat' },
});
```

After the callback, retrieve `initialMessageId` via `list_child_sessions` and pass
it with `child.cloudAgentSessionId` to `get_message_result`. Authorized follow-up:

```js
const { messageId } = await generate_message_id({});
await send_message({
  cloudAgentSessionId: child.cloudAgentSessionId, messageId,
  payload: { type: 'prompt', prompt: followUpTask, mode: 'code', model: modelId },
  autoCommit: false,
});
```

After the callback, or as one bounded check:

```js
await get_message_result({ cloudAgentSessionId: child.cloudAgentSessionId, messageId });
```

## Reporting feedback and bugs

Report bugs, confusing behavior, and feature requests about the Kilo platform
through `feedback.submit` — the HTTP `POST /feedback` endpoint does the same
thing. Batch everything you want to report into one submission instead of
sending several: the endpoint accepts one submission per authenticated user per
minute, and a second call within a minute is refused with a message asking you
to batch. MCP error responses also point agents here, so treat this as the place
to send platform feedback and bug reports rather than a support channel.
