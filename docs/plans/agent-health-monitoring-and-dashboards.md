# Agent Health: Dashboard and Monitoring Plan

Status: proposed, 2026-09-28. This is a plan, not an implemented dashboard, approved SLO, or monitor configuration.

## Goal and scope

Give someone unfamiliar with agent internals an answer at a glance to four questions: can users finish work, did that get worse or better and when, how many requests were affected, and where should an investigator look next? Axiom is the intended home for the shared operational overview, historical graphs, and eventually monitors. The first release prioritizes trustworthy dashboards; monitors follow after coverage and baselines are measured.

Initial scope is interactive Cloud Agent and Code Reviewer. Code Reviewer needs two distinct views: the health of its Cloud Agent executions, and the final outcome of the review requested by a user. Security Agent, auto-fix, auto-triage, Gastown, model gateway, and general Worker HTTP error rates do not become part of a combined agent success rate. Add another product only when its owner, unit of work, and authoritative outcome have been defined.

## Findings from the current audit

- Cloud Agent already emits `cloud_agent_outcome_aggregate` for 5-, 15-, and 60-minute windows and `cloud_agent_open_stock` roughly every three minutes. They derive from durable reports in `cloud_agent_sessions` and `cloud_agent_session_runs`; see `services/cloud-agent-next/src/telemetry/outcome-aggregate.ts`, `open-stock.ts`, and `report-store.ts`. Recent emissions and `cloud-agent-next` Logpush ingestion were observed in the Axiom `cloudflare-logpush` dataset during the audit.
- Outcome rollups split by legacy/control generation and initial/follow-up turn, but not by product origin. The reporting session table does not store origin (`packages/db/src/schema.ts`, `cloud_agent_sessions`). Code Reviewer supplies trusted `createdOnPlatform: 'code-review'` at preparation (`services/code-review-infra/src/code-review-orchestrator.ts`), but this value does not reach the reporting aggregate.
- The admin Code Reviews page, `apps/web/src/app/admin/code-reviews/page.tsx`, reads PostgreSQL through `admin-code-reviews-router.ts`. It already has live queue health, terminal outcome KPIs, wait percentiles, daily status charts, duration trends, segmentation, and error drill-downs. The `kilo-code-review-worker` sends operational logs to Axiom, but there is no verified Axiom aggregate of final review outcomes. Worker requests and retry attempts must not substitute for reviews.
- The admin Failure Rate is `(failed excluding billing and model-not-found + interrupted) / terminal reviews`, not platform-attributed failure. Its daily chart divides completions by all reviews, including in-progress work, whereas the headline success KPI divides by terminal reviews. The “Avg Run Time” query can include non-completed terminal reviews with timestamps despite the card text saying completed reviews. Do not copy these ambiguous definitions into an SLO without resolving them.
- Existing saved Axiom dashboards could not be inspected because the browser UI required login. This plan must start with an inventory of their actual queries and owners rather than assume that the current layouts are absent or redundant.

## Measurement contracts

| Signal | Unit and calculation | Authority | Important exclusions or caveats |
| --- | --- | --- | --- |
| Cloud Agent platform failure share | `platformFailed / settled`, with both counts shown. One admitted message/turn is one unit. | Cloud Agent run reports, existing outcome aggregate. | `settled = completed + platformFailed + providerFailed + userFailed + unknownFailed`; interrupted is separate. Pre-admission requests are not in this denominator. |
| Code Reviewer agent platform failure share | Same Cloud Agent definition, filtered to a validated, stored `code-review` origin. | Same Cloud Agent reports and classification, not an independently inferred review failure reason. | One review can have multiple attempts, sessions, or turns. This measures execution attempts, not final review delivery. Keep origin-missing work visible as unknown. |
| Completed review share | `completed final reviews / eligible terminal final reviews`, with counts and explicit buckets for other terminal outcomes. One review ID is one unit. | `cloud_agent_code_reviews`, not Cloud Agent execution logs or `cloud_agent_code_review_attempts`. | Exactly define eligibility, terminal time, cancellations, billing, model-unavailable, superseded and reaped reviews before calling it an SLO. A retry must not increment the review denominator. |
| Review system failure share | Non-benign terminal review failures / agreed eligible final-review denominator. Show the count and reasons. | Final review rows and `CODE_REVIEW_BENIGN_TERMINAL_REASONS` in `packages/db/src/schema-types.ts`. | This is a broad review-system diagnostic, **not** the Cloud Agent platform-failure signal and not automatically the admin Failure Rate. Show unknown classification separately. |
| Work waiting | Queued/accepted turns and oldest reported age; pending reviews >5 minutes, oldest pending age, stale queued claims, running >90 minutes. | Cloud Agent open-stock rollup; Code Reviews admin queue query. | Age is not proof of a stall. Accepted is not proof that a sandbox is alive. Review queue stock is a snapshot, not a count of new reviews. |
| Review start latency | Fraction of started reviews with valid `started_at - created_at <= 5 minutes`, plus p95 and denominator. | Code Reviews admin query. | Rows not yet started are excluded from the historical fraction; pair it with the live pending-over-five-minutes count so stuck work cannot improve the rate by being absent. |
| Data availability | Last successful collection, missed/failed collections, lag, coverage, and number of eligible units. | Collection envelopes and independently checked reporting lag. | Missing data, no traffic, and observed zero failures must be three different states. |

“Reviews delivered successfully” is shorthand for a final `completed` review row. Before using the word *delivered* in an SLO or monitor, validate that this state always follows the required review publication or dashboard-result persistence for each supported review mode. If not, name the current metric “reviews completed” and separately instrument publication success. Avoid claiming an externally published PR comment or check from a Cloud Agent terminal event.

For historical review rates, prefer a well-defined terminal-outcome window with a stable terminal timestamp. Audit all paths that terminalize a review, including pre-dispatch failure, callback, cancellation, supersession and stale reaping, before choosing `completed_at` or adding a dedicated terminal timestamp. The admin historical filter currently cohorts by creation date; its KPI will not necessarily match an outcome-time chart for the same range. Document both views and reconcile them on comparable cohorts rather than silently treating them as identical. Never use a mutable `updated_at` without checking whether later writes can shift an outcome into another window.

## Data work

### A. Attribute Cloud Agent executions to Code Reviewer

1. Trace the trusted `createdOnPlatform` value from code-review preparation through stored session metadata, create-session report, reporting queue contract, `cloud_agent_sessions`, and outcome/open-stock collection. Store a bounded product-origin value at the reporting boundary. Publicly supplied or unrecognized origin strings must not be allowed to impersonate Code Reviewer; retain an explicit unknown/other bucket.
2. Emit bounded `code-review` outcome and open-stock aggregates from the same database snapshot and failure-classification owner as the general Cloud Agent aggregate. Keep their contract version, window start/end, collection timestamp, status, coverage, generation, role, numerator, denominator and unknown/interrupted counts. Do not join arbitrary Axiom request logs by session ID to assemble the denominator.
3. Preserve existing general Cloud Agent series and report consumers. Treat old sessions lacking origin as unknown; do not silently backfill with a guessed origin. A historical backfill is optional only if an authoritative session-to-review linkage can be proved and the resulting coverage is labeled.
4. Check a review with one session, a review retried on a fresh session, an interrupted execution, and a pre-admission failure. Confirm that the first three produce the intended execution units and that the fourth is absent from the execution denominator but present in review health.

### B. Export final review health to Axiom

1. Reuse `cloud_agent_code_reviews` as the final-outcome authority and the existing reason vocabulary/benign-reason policy. Do not make `code-review-infra` log messages a second source of truth. Derive a bounded periodic snapshot in the component that owns review database access; emit only aggregate counts and safe categorical labels to Axiom, not PR text, repository names, error messages, identities, or credentials.
2. Publish versioned 5/15/60-minute outcome windows and a separate open-stock snapshot at a documented cadence. Include `evaluationId`, window bounds, observed/collection times, population/retention label, `collectionStatus`, count by final status, benign/system/unknown reason buckets, total denominator, and query latency. Failed collections must emit an explicit failed envelope, not a zero-filled success result. Keep retry-attempt counts as drill-down diagnostics only.
3. Decide and test the terminal time and eligibility contract before implementing the query. Review how council versus standard, manual dashboard-only versus provider-published, GitHub/GitLab/Bitbucket, superseded, reaped, and pre-dispatch reviews map to final status. Include explicit zero-traffic and zero-denominator handling. Make any intentionally excluded populations visible.
4. Reconcile new aggregates against admin PostgreSQL queries over matched cohorts and time windows; investigate mismatches by reason, review type, and origin. Verify that successful retry yields one final completed review even if an earlier agent session platform-failed. Verify a failed publication or callback can yield a failed review despite a completed Cloud Agent turn.

### C. Establish trust in both feeds

- Measure report-queue delivery and terminal-report lag, including the real distribution relative to the Cloud Agent rollup's provisional two-minute allowance. Inspect missing-parent/dropped reports and the report queue/DLQ; lost reports can undercount failures and open stock.
- Check that all expected 5/15/60-minute series arrive, only complete collections count, the expected generations are present, and the latest evaluated window is recent. One scheduled event may contain several window records; deduplicate by `evaluationId`/window. Never sum overlapping rolling windows or treat each repeated snapshot as new work.
- Measure new review snapshot lag and reconcile it with DB state over several ordinary and failure-heavy windows before surfacing an SLO number. Baseline query cost and Axiom ingestion volume; keep aggregate output low-cardinality and exclude raw IDs.
- Keep these known coverage limits near the dashboard definitions: Cloud Agent reporting population is retained for 90 days, classification has unknown cases, provider includes some user model-selection errors, and open-stock age does not prove a stall. Separate failures before admission from admitted-turn failures.

## Axiom dashboard layout

**Shared Agent Health overview:** the default should answer health at a glance, not present an unweighted composite score. Two service sections, Cloud Agent and Code Reviewer, each show the latest complete snapshot, a small “as of” timestamp, denominator, counts, and trend in the selected time range. Code Reviewer has two adjacent headlines: **Review agent platform failures** (execution units) and **Reviews completed** (final review units). They must never share a denominator or be added together.

1. Header: environment, UTC/local time explanation, range selector (24 hours by default; 7 days for context), last complete observation per feed, and a clear stale/missing/no-traffic indicator. State that only production series are shown. Deployment annotations should be displayed only if their timestamp and deployment identity are trustworthy for the affected service.
2. Cloud Agent row: platform-failure share with numerator/denominator; completed, provider/user/unknown failed and interrupted counts; queued/accepted stock and oldest age. Timeline pairs outcome rate with volume; separate stock and age timeline. Filters: legacy/control and initial/follow-up, with combined view as default.
3. Code Reviewer row: origin-filtered Cloud Agent platform-failure share and final review completion share side by side, each with its own sample size. Add pending-over-five-minutes, oldest pending, started-within-five-minutes, p95 wait, and running-over-90-minutes as a compact queue/latency strip. Timelines distinguish execution outcomes, final review outcomes, and queue health.
4. Drill-down: Cloud Agent stage/code/responsibility breakdown and open-stock details; Code Reviewer final reasons, cancellations, retry attempts, review mode, and admin dashboard link. Keep per-request investigation and sensitive data in existing authorized admin/log tools, not in overview panels.
5. Each chart tooltip or adjacent definition states its numerator, denominator, source, freshness and limitations. A gap represents missing data; zero traffic is labeled “no eligible work”; zero observed failures with volume is labeled “0 failures.” Show counts with rates, and avoid axes or stacked rates that make a small sample look like a large incident.

Before building, inventory saved Axiom dashboards and verify whether any query/panel can be reused or linked. Store canonical metric definitions, APL queries, and panel/monitor ownership in a version-controlled location even if Axiom UI objects must initially be configured manually. Record the actual dashboard URLs and query versions after creation so the implementation can be audited.

## Monitoring rollout (after dashboard validation)

Monitors should detect a user-impacting regression and an observability failure separately. Do not choose an SLO target from a dashboard label or reuse an existing code-review alert threshold without baseline evidence.

| Monitor family | Candidate signal and safeguard | Routing intent |
| --- | --- | --- |
| Agent execution | Cloud Agent and review-origin platform failure share, with numerator, denominator, minimum sample size, unknown-share guard, and sustained short/long windows. Split product only where origin coverage is verified. | Page only for sustained, actionable platform impact; ticket for lower-volume deterioration. |
| End-to-end reviews | Final-review non-benign failure/completion rate, plus pending-over-five-minutes and running-over-90-minutes stock. A completion percentage on its own is delayed by long-running work. | Page for a proven active backlog/delivery outage; ticket for sustained trend change. |
| Latency | Review started-within-five-minutes rate paired with pending-age stock; later add Cloud Agent queue-to-activity latency once measured reliably. | Initially ticket; page only for a verified widespread blockage. |
| Telemetry integrity | Missed/failed collection, excessive lag, missing origin coverage, unknown classifications, report-queue backlog or DLQ. | Route as “health unknown,” not “service healthy” or “service down”; page if a blind spot prevents detecting serious incidents for a sustained period. |

For each monitor, specify an owner, runbook, evaluation cadence, short and long observation windows, minimum numerator and denominator, low-traffic behavior, deduplication/cooldown, and recovery condition. Compare monitor decisions with incident examples and quiet periods before enabling paging. Review whether the existing BetterStack `/api/code-reviews/up` slow-review/error-spike checks overlap; retain them until replacement monitors prove equivalent coverage, then avoid duplicate pages. Add Axiom monitors last, with a dry-run/ticket period and a documented rollback path.

## Delivery sequence and acceptance

1. **Inventory and contracts:** inspect existing Axiom dashboards with an authenticated owner, capture links/query definitions, and approve units, exclusions, terminal timestamps and ownership. Outcome: one unambiguous definition per panel and monitor candidate.
2. **Cloud Agent origin slice:** extend and test reporting, migration and aggregate contracts, deploy via the normal owner-controlled workflow, and compare review-origin sample coverage with review attempts. Outcome: the new Axiom series is complete enough to show with an explicit origin coverage indicator; general Cloud Agent numbers do not change unexpectedly.
3. **Review final-outcome feed:** implement and validate the DB-derived aggregate, including pre-session failures and retry outcomes. Outcome: counts reconcile to the admin database for identical populations/windows; collection failures are distinguishable from zero work.
4. **Dashboard:** build one overview plus service-specific drill-downs and link existing admin tools. Have a non-specialist answer “is it healthy?”, “what changed when?”, “how many were affected?” and “where next?” without oral guidance. Outcome: the answers and definitions match the sources, and 24-hour/7-day trend panels reveal missing samples.
5. **Monitoring:** collect baseline data, approve provisional objectives and an error-budget policy, dry-run the candidate monitors, then enable ticket/page routing with named owners and runbooks. Outcome: test incidents trigger the correct signal; provider/user/benign events and missing telemetry do not get mislabeled as platform failures.

No target percentages, page thresholds, burn-rate multipliers, or calendar commitment are approved by this document. Those are decisions after ingestion, classification and reporting lag have been measured. The standalone `agent-health-dashboard-preview.html` is a local, illustrative layout, not a production dashboard or evidence of current health.

## Contract decisions implemented for the data work (2026-09-28)

- **Flat health events, one aligned bucket.** The nested envelopes are gone. Worker and web emit flat rows whose `metric` is one of `agent_execution`, `agent_failure`, `agent_setup_failure`, `agent_open`, `review_outcome`, `review_reason`, `review_start`, `review_open`. Windowed collectors run every five minutes and close one 5-minute bucket `[windowStart, windowEnd)`, stamping the same `observedAt` (`now.toISOString()`) on every row of an attempt. `agent_open` and `review_open` are snapshots and have no window. Scheduled invocations normally emit one observation per bucket; platform retries or missed invocations can still duplicate or omit one.
- **Zero is success; absence is a miss.** Headlines are emitted even when zero, and zero breakdown rows are omitted. A collector whose query fails logs one `{ metric: "collection", collector, observedAt, status: "failed" }` row and no counts (the web adds `environment`). A zero headline is a success; a `collection` row means a failed attempt, not zero traffic.
- **Review reason classes.** Stored reasons are classified as `benign` (`model_not_found` stays benign), `unknown` (literal `unknown`), or `system` (every other recognized reason). Null or out-of-vocabulary reasons collapse to one `unrecognized` row with class `unknown`. The raw string is not logged. The identity `benign + system + unknown = failed + cancelled + interrupted` holds and is not stored as a residual field. No reason class appears on the `review_outcome` row.
- **Aligned execution and review windows.** Both collectors subtract a provisional two-minute reporting allowance before flooring to the five-minute boundary. Cloud Agent uses the scheduled slot time for its window (falling back to wall clock when unavailable), while web uses wall clock; `observedAt` remains the collection time. Review `completed` is stored status, not publication, and the admin Failure Rate is not copied.
- **No monitors, dashboards, SLO numbers, or Axiom resources** are part of this data work.
