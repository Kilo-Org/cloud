Separate transport, policy, and state

One shared SCM module inside the existing Worker codebase. SandboxControl supplies durable state and serialized operations.

One business-logic owner

Shared SCM credential module

  • Parse authorization and select the grant.
  • Check ownership, expiry, allocation, and target.
  • Issue or renew bound capabilities.
  • Redeem through git-token-service.
  • Forward requests and apply common retry rules.
Admission runs with the DO’s serialized state access. HTTP forwarding runs in the Worker. Both use the same module.
Durable coordinator

SandboxControl

  • Own allocation and wrapper lifecycle.
  • Store grants and session membership.
  • Serialize reads and updates.
  • Reject operations for replaced allocations.

Small entry points delegate credential decisions to the shared module.

One policy for both providers. Issuance and renewal use Cloudflare’s configured authorization behavior, including permitted user-authorization fallback. Vercel-only permission overrides are removed.

git-token-service remains the authority for GitHub, GitLab, and Bitbucket token issuance and redemption. Sandbox adapters do not select permissions.

03

Preparation and renewal use the same owner

Session preparation

Create a grant once

  1. SandboxControl selects the allocation and calls the shared credential module.
  2. The module applies the common repository policy and requests a bound capability from git-token-service.
  3. SandboxControl persists the grant: alias, capability, membership, expiry, and sandbox binding.
  4. The provider interface installs the required network interception or forwarding.
  5. The wrapper receives the SCM alias and the separate Kilo runtime handle.
Renewal and retirement

Keep durable state authoritative

  1. The shared module checks whether the capability needs renewal.
  2. It renews through git-token-service with the same policy on either provider.
  3. It checks the current allocation and grant again before persisting the replacement.
  4. The alias remains stable during capability renewal.
  5. After allocation retirement, new requests using the old binding are rejected. Already admitted requests can finish.

Why does the current class say SandboxControlV2?

The name came from the control-plane replacement. Production already exports it as SandboxControl. This refactor preserves the internal name, deployed bindings, and migration history.

What remains different between sandbox providers?

Identity evidence, proxy transport, network configuration, and provider lifecycle API calls. Cloudflare also retains its existing direct capability entry for compatibility. Vercel accepts aliases and requires verified provider identity. Native restricted egress keeps its existing port restrictions.

Does Cloudflare behavior change?

Configured GitHub permissions remain unchanged. Shared admission adds current membership, target, and allocation checks to native alias requests. Mixed managed and caller-owned authorization now fails before forwarding. Denied managed requests never fall back to caller-owned authorization.

Is this already running?

The refactor is implemented in this worktree and verified with local unit and Workers tests. It has not been deployed. Provider identity tests use synthetic evidence; this task did not verify live provider interception or remote Git operations. Vercel is not used in production.
